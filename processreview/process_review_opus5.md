## 요약

설계의 뼈대 — 단계 분리, 다중 후보 비교, 짧은 프롬프트, 임포터 규격 전담, 고정 타이밍 격자 — 는
타당하고 Remotion·TTS 구현도 그 사양과 맞는다. `tsc --noEmit` 통과, `hackers.csv` 1,200행의 DAY별
40개·번호 연속·전역 중복 0·스키마 정규식 위반 0 을 확인했다. 타이밍 상수도 계산이 맞고, TTS 슬롯 여유는
실제로 모델을 돌려 재봤을 때 충분했다.

그러나 **v2 의 핵심 방어선 두 개가 실제로는 작동하지 않는다.** ① `WHY.md` 가 "검사기가 막는다"고 적은
이미지 프롬프트 금지 규칙을 검사기가 전혀 보지 않는다(금지어를 전부 넣은 프롬프트가 `errors: []` 로
통과). ② 단색 밴드를 잘라낸다는 임포터의 트림 임계값이 16:9 정확 케이스(0.5625)보다 **1.3%p 위**에
있어서, 밴드가 조금만 더 크면 잘리지 않고 그대로 최종 이미지에 남는다(실측 재현). 이 둘은 2단계에서
2,400장을 만들기 전에 고쳐야 한다.

그 밖에 `req.txt` 가 v2 규칙과 정면 충돌하는 구프로젝트 사양인 채로 1단계 AI 에게 필독 문서로
지정돼 있고, 4단계 무인 배치는 예외 하나로 120세트가 통째로 멈추며, 렌더 후 QA 는 실행할 코드 자체가
없다. **1단계 착수 전에 치명적 1·2·7 을, 2단계 착수 전에 3·5, 4단계 착수 전에 4·6 을 처리하면
현재 구조로 120편 완주가 가능하다.** 구조를 바꿀 필요는 없다.

## 근거가 확인된 결정 (건드리지 말 것)

`WHY.md` 의 결정 중 직접 확인해 타당하다고 판단한 것들이다.

- **1번 (단계별 통짜 진행)** — 단계 경계가 그대로 파일 산출물이라 세션 간 컨텍스트 인계가 필요 없다. 코드 구조가 실제로 그렇게 돼 있다.
- **2번 (프롬프트 단순화)** — 결정 자체는 유효하다. **다만 집행 장치가 없다**(치명적 1번). 근거를 반박하는 것이 아니라, 근거대로 동작하게 만드는 문제다.
- **3번 (규격 책임을 임포터로)** — 방향은 옳다. 파일명 매칭·PNG 변환·north 크롭 모두 의도대로 동작한다. 고칠 것은 트림 **임계값 하나**다(치명적 3번).
- **4번 (다중 AI 후보)** — IPA·의미 정확도는 어떤 스크립트도 못 잡는다. `validate-content` 가 잡는 것이 형식뿐이라는 서술은 코드를 읽어 사실로 확인했다.
- **5번 (생성과 검증 분리)** — `요청문/3` 이 수정 금지·보고 형식 고정까지 명시하고 있어 실행 가능하다.
- **7번 (텍스트 전용 git)** — 최종 이미지만 2,400장 × 평균 2.85MB ≈ **6.8GB**, 영상 6.6GB, author 3벌이면 후보만 20GB 다(샘플 PNG 실측 2.4~3.3MB 기준). git 에 넣을 물건이 아니다. C: 여유 1.5TB 라 디스크는 문제없다.
- **8번 (타이밍 격자·화자 순환·속도 상수)** — 계산과 실측 모두 맞는다. `constants.ts` 의 유도값이 `build_set_audio.py` 슬롯과 정확히 일치하고(예문 화면 11.9초 / 예문 음성 13.4초), **가장 긴 단어 15개를 실제 배정 화자로 합성해 보니 전부 word1 예산 1.05초 안에 들어왔다**(최댓값 `misunderstanding`/Erinome 1.008초, 여유 +0.042초 — 부록 A-6). 압축 없이도 통과하므로 단어 슬롯 overflow 위험은 낮다.
- **10번 (버린 대안)** — 재제안하지 않는다.

## 열린 질문 (사용자가 답해야 결정된다)

1. **2,400장의 주 수급 도구를 무엇으로 확정할 것인가.** 이것이 2단계 소요를 결정한다. agy 실측(3장 26초)이면 약 5.8시간이지만 429 쿼터가 변수이고, Codex 순차(장당 60~90초)면 **40~60시간**이라 현실적이지 않다. 도구가 정해져야 치명적 1·3번의 우선순위와 `--escalate` 운용 방식도 정해진다.
2. **콘텐츠 후보를 몇 벌 받을 것인가.** `WHY.md` 4장의 "DAY 01~10 만 3벌로 품질 차이 확인" 방침을 그대로 갈 것인지. 이미지 후보를 몇 벌 받을지는 저장 용량(벌당 6.8GB)과 3단계 인건비에 직결된다.
3. **3단계 선별 인건비를 감당할 것인가.** 세트당 20칸 대지 × 120세트 × author 수. 3벌이면 대지 360장이다. OCR 기반 글자 혼입 1차 자동 탈락을 넣으면 사람이 볼 양이 줄어드는데, 도입할 것인가(`WHY.md` 11장이 이미 여지를 열어 뒀다).
4. **정의 낭독 속도**(개선 1번). 실효 2.83~4.09 단어/초 vs 정책 목표 2.6. 예산은 2.1~3.4초 남는다. 현재를 수용할지, `MAX_SLOWDOWN_RATIO` 를 올릴지, 정의 상한을 10단어로 줄일지는 사용자 결정 사항이다.
5. **원격 저장소와 v1 처분** (`WHY.md` 11장). v2 는 로컬 git 뿐이다. 1단계 산출물(120세트 × 3벌의 텍스트)이 쌓이기 시작하면 백업 없는 상태의 위험이 커진다.

## 부록 — 이번 검토에서 실제로 돌린 것

모두 읽기·실행만 했고 저장소 파일은 수정하지 않았다. TTS 캐시는 프로젝트가 아닌 임시 폴더에 썼다.

### A-1. 금지어를 전부 넣은 프롬프트가 통과한다

`validateImagePrompts` 에 아래 프롬프트를 넣었다.

```text
## 01_chore_word.png
A cheerful robot sweeps a cozy living room, 16:9 aspect ratio, 1920x1080,
dramatic cinematic lighting, no logo, no watermark, leave the bottom 24% blank,
Pixar style. Stylized 3D cartoon illustration, square. No text.
```

출력: `errors: []` / `warnings: []` (장면부 31단어라 경고 상한 30 도 아슬아슬하게만 넘지 않는다)

### A-2. 트림 임계값 경계 실측

1024×1024 캔버스에 컨텐츠를 넣고 위아래를 단색으로 채운 뒤 `import-images.mjs` 와 동일한 로직을 돌렸다.

| 컨텐츠 높이 | 밴드 비율 | 트림 후 면적비 | 트림 판정 | 최종 1600×900 의 단색 비율 |
|---|---|---|---|---|
| 1024×576 (정확한 16:9) | 44% | 0.563 | **적용** | 정상 복구 |
| 1024×540 | 47% | 0.527 | **되돌림** | **41%** |
| 1024×512 (2:1) | 50% | 0.500 | **되돌림** | **42%** |
| 1024×460 | 55% | 0.449 | **되돌림** | **47%** |

`WHY.md` 가 근거로 든 44% 케이스는 임계값 0.55 를 0.013 차이로 통과한 것이다. 47% 부터는 밴드가 최종
