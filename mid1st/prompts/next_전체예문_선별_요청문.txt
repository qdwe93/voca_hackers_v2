기존 파일이 이미 있으면 덮어쓰지 마라. 유효한 완성 파일이면 검증만 하고, 불완전한 파일이면
내용을 보존한 채 중단하여 재작업 범위를 보고하라. 이 세션에서 방금 새로 만든 파일의 검증
오류만 직접 고칠 수 있다.

먼저 아래 게이트를 전부 실행하라.

  node mid1st/scripts/validate-assignments.mjs
  node mid1st/scripts/validate-calibration-selection.mjs --max 12
  node mid1st/scripts/validate-candidates.mjs --author codex
  node mid1st/scripts/validate-candidates.mjs --author antigravity
  node mid1st/scripts/validate-candidates.mjs --author claude

하나라도 FAIL이면 부분 결과를 채우거나 선별을 시작하지 말고 정확한 실패 항목만 보고하라.
모두 PASS이면 다음 명령으로 비교표를 만든다.

  node mid1st/scripts/compare-candidates.mjs

중요: 위 후보 검증의 PASS는 ID·경로·strict 형식·exact word·8~12단어만 보장한다. 단어 뜻,
품사, 교과 개념, 문법과 사실의 정확성은 보장하지 않는다. author의 run_report나 자체 설명을
정답으로 믿지 말고, 반드시 word_inventory의 meaningKo·partOfSpeech·definition과 실제 후보
문장을 직접 대조하라.

이미 확인된 예시로 DAY06-11 `object`의 확정값은 명사 `물건`, definition은
`a thing you can see and touch`이다. Antigravity 후보는 `object to ...`라는 동사 `반대하다`
뜻으로 써서 형식 검증은 통과했지만 의미상 탈락이다. 이 사례는 특정 author를 불리하게
평가하라는 뜻이 아니다. 모든 author와 baseline을 모든 단어에서 같은 방식으로 검사하라는
경고다.

각 단어는 다음 순서로 판단하라. 앞 기준을 희생해 뒤 기준을 얻지 마라.

1. 확정 meaningKo·partOfSpeech·definition과 정확히 같은 뜻인가
2. exact word가 그 뜻과 품사로 자연스럽게 사용됐는가
3. direct/contextual 배정이면 conceptId와 conceptCueKo의 사실·관계가 문장 안에 직접 보이는가
4. day_fallback이면 DAY 주제와 단어 뜻이 직접 보이는가
5. word_fallback이면 단어 뜻이 가장 선명한가
6. 비유·은유·상징·의인화·말장난이 아닌 문자적 표현인가
7. 영어 문법과 교과 사실이 정확한가
8. 초6이 읽기 쉽고 8~12단어인가
9. 안전하고 한 장면이나 한 과정으로 시각화하기 쉬운가
10. 위 기준이 동률일 때만 selected_examples의 사용자 선호를 적용하는가

fallback이라는 이유만으로 감점하지 마라. 억지 교과 연결보다 정확한 fallback이 낫다.
특정 author를 우대하지 말고 baseline도 동등한 네 번째 후보다. 대표 선택에서는 author의 득표
수가 아니라 preferenceNoteKo와 선택 문장의 관찰 가능한 품질 기준만 일반화하라.

먼저 assignment에서 reviewRequired=true인 48개와 각 validation_report의 휴리스틱 메모를
주의해서 보되, 거기에 없는 단어도 생략하지 말고 1,200개 전부 의미 검토하라. 휴리스틱 경고는
자동 탈락 사유가 아니며 실제 문맥을 보고 판단한다.

표현 차이뿐이거나 우열이 분명하면 사용자에게 묻지 말고 자동 추천하라. 아래 경우만
reviewRequired로 남긴다.

- 후보들이 확정 뜻이나 품사를 서로 다르게 해석한다
- 단어 뜻이 좋은 후보와 교과 개념이 좋은 후보가 달라 절충이 필요하다
- 사실성·문법·비유 여부를 확정하기 어렵다
- 네 문장이 모두 하나 이상의 핵심 기준을 위반한다
- 수동 수정안이 필요하거나 두 후보의 의미 차이가 커 사용자 판단이 필요하다

모든 1,200단어의 추천을 mid1st/final/selection_manifest.jsonl에 inventory 순서대로 저장하라.
각 줄은 다음 네 키만 갖는다.

  {"wordId":"DAY01-01","selectedAuthor":"codex","sentenceOverride":null,"note":"auto: 짧고 구체적인 근거"}

- selectedAuthor: codex | antigravity | claude | baseline | manual
- manual일 때만 sentenceOverride에 8~12단어의 수정 문장을 쓴다
- 다른 author를 고르면 sentenceOverride는 반드시 null이다
- 고확신 추천 note는 `auto:`, 사용자 확인이 필요한 note는 `reviewRequired:`로 시작한다
- 선택한 author의 문장을 수정하지 마라. 수정이 필요하면 manual을 쓴다

reviewRequired 항목만 mid1st/reports/selection-review.md에 inventory 순서로 모아라. 각 항목에는
wordId, word, 확정 뜻·품사·definition, PART·DAY, 개념 이름·matchMode·conceptCueKo, baseline과
세 후보, 현재 추천, 구체적인 검토 이유, manual 수정안이 있으면 그 문장을 포함한다.

보고서 첫머리에는 다음 수치를 적어라.

- 자동 추천 수
- reviewRequired 수
- baseline·codex·antigravity·claude·manual별 추천 수
- 확정 뜻/품사 불일치로 탈락한 후보 수와 author별 수
- 교과 개념 직접성 부족으로 탈락한 후보 수와 author별 수

manifest 작성 후 반드시 실행하라.

  node mid1st/scripts/build-final.mjs --dry-run

FAIL이면 이 세션이 방금 만든 manifest의 오류만 수정하고 재검증하라. reviewRequired가 하나라도
있으면 실제 build-final은 실행하지 말고 사용자 선택을 기다려라. reviewRequired가 0개여도 이
요청에서는 final_sentences.jsonl을 만들지 말고 dry-run까지만 수행하라.
