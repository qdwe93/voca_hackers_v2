단어 철자, 품사(partOfSpeech), 한국어 뜻(meaningKo), IPA, 예문(sentence)은 사용자가 확정한
값이다. 절대 바꾸지 마라. 마음에 들지 않아도 바꾸지 마라.

시작 전에 다음 두 파일을 읽어 프로젝트 규칙을 파악하라.

    mid1st/AGENTS.md
    mid1st/DECISIONS.md

## 3. 이미 끝난 일과 입력 위치

1,200개 영영 정의를 두 모델이 각각 다시 썼다. 결과는 아래에 있다.

    tmp/defs/RULES.md                  두 모델에게 준 동일한 작성 규칙
    tmp/defs/in/chunk01~12.jsonl       입력 1,200줄 (100줄씩 12개)
    tmp/defs/claude/chunk01~12.jsonl   Claude Opus(medium) 결과 1,200줄
    tmp/defs/codex/chunk01~12.jsonl    GPT-5(high) 결과 1,200줄

tmp/defs 안의 .py 파일은 앞 단계에서 쓰고 버린 보조 스크립트다. 무시하라.

**tmp/defs/RULES.md를 반드시 처음부터 끝까지 읽어라.** 정의를 직접 고쳐야 할 때 그 규칙을
그대로 지켜야 한다.

두 결과 모두 아래 일곱 키를 쓰는 strict JSONL이며 입력과 같은 순서다.

    wordId, word, definitionOld, definitionNew, sentenceFit, reviewRequired, reviewReason

sentenceFit은 ok | unclear | mismatch 이고, 앞 세션에서 집계한 값은 다음과 같다.

    claude: ok 1154 / unclear 42 / mismatch 4
    codex:  ok 1141 / unclear 40 / mismatch 19

시작할 때 다음 명령으로 위 수치를 다시 확인하라. 수가 다르면 그대로 보고하고 멈춰라.

    node -e "const fs=require('fs');for(const lane of ['claude','codex']){let n=0,bad=0,f={};for(let i=1;i<=12;i++){const p='tmp/defs/'+lane+'/chunk'+String(i).padStart(2,'0')+'.jsonl';for(const l of fs.readFileSync(p,'utf8').trim().split('\n')){n++;const o=JSON.parse(l);if(Object.keys(o).join(',')!=='wordId,word,definitionOld,definitionNew,sentenceFit,reviewRequired,reviewReason')bad++;f[o.sentenceFit]=(f[o.sentenceFit]||0)+1;}}console.log(lane,n,bad,JSON.stringify(f));}"

## 5. 1단계 — 기계 검증기 작성

두 모델 결과를 같은 기준으로 검증하는 스크립트를 새로 만들어라. 기존 스크립트는 수정하지 마라.

    mid1st/scripts/validate-definitions.mjs

저장소에 공용 헬퍼가 있으니 재사용하라. `mid1st/scripts/lib.mjs`가 다음을 export 한다.

    defaultPath(...parts)          mid1st 기준 경로 결합
    parseArgs(argv)                --key value 파싱
    readJsonl(path)                [{ value, line }] 배열 반환
    strictKeys(obj, keys, label, errors)
    englishWords(sentence)         영어 낱말 배열 (단어 수 세기용)
    containsExactWord(sentence, word)
    loadInventory(path)

**단어 수는 반드시 englishWords()로 센다.** 이 함수는 하이픈을 낱말 경계로 보므로
`eco-friendly`는 2단어로 계산된다. 프로젝트 다른 검증기와 같은 기준을 쓰기 위한 것이다.

사용법:

    node mid1st/scripts/validate-definitions.mjs <대상파일> [--report <경로>]

검증기는 결정론적으로 다음을 확인하고 위반 목록(파일·줄 번호·wordId·사유)을 출력한다.

    (1) 정확히 1,200줄이고 wordId가 final_sentences.jsonl과 같은 순서로 일치한다
    (2) 각 줄이 정해진 키만 갖는다 (중간 산출물은 7키, 최종본은 9키)
    (3) definitionOld가 final_sentences.jsonl의 definition과 완전히 같다
    (4) definitionNew가 1단어 이상 7단어 이하다
    (5) definitionNew에 표제어나 그 변화형이 들어 있지 않다
        어미 변화까지 본다: -s, -es, -ed, -d, -ing, -er, -est, -ly,
        자음 중복형(stop→stopping), y→i 변화형(carry→carried)
    (6) definitionNew가 마침표로 끝나지 않는다
    (7) definitionNew의 첫 글자가 소문자다 (고유명사로 시작하는 경우만 예외로 보고만 한다)
    (8) sentenceFit이 ok | unclear | mismatch 중 하나다
    (9) reviewRequired가 true면 reviewReason이 비어 있지 않다

주의: **7단어 제한은 definitionNew에만 적용한다.** definitionOld는 기존 확정값이라
7단어를 넘는 것이 정상이므로 길이를 검사하지 마라.

두 모델 결과 각각에 대해 실행해 위반 건수를 얻어라. 이 수치는 2단계 선택과 보고서에 쓴다.

    node mid1st/scripts/validate-definitions.mjs tmp/defs/claude
    node mid1st/scripts/validate-definitions.mjs tmp/defs/codex

(청크 12개를 이어 붙여 검사해도 되고 폴더를 받아 처리해도 된다. 방식은 자유다.)

## 6. 2단계 — 단어별 선택

1,200단어마다 claude와 codex의 definitionNew 중 하나를 고른다. 아래 순서대로 적용하고,
앞 기준에서 결정되면 뒤 기준을 보지 마라.

    1. 기계 검증을 통과하지 못한 쪽을 먼저 탈락시킨다. 한쪽만 통과하면 통과한 쪽을 쓴다.
    2. 둘 다 통과하면 확정 뜻과의 정확성을 본다. meaningKo와 partOfSpeech가 가리키는 뜻을
       좁히거나 넓히지 않고 그대로 담은 쪽을 고른다.
    3. 예문 속 쓰임과 어긋나지 않는 쪽을 고른다. final_sentences.jsonl의 sentence를 함께 읽어라.
    4. 더 쉬운 쪽을 고른다. 흔한 낱말, 짧은 구조, 3음절 이상 단어가 적은 쪽이다.
    5. 순환 정의에 가깝지 않은 쪽을 고른다. 표제어의 동의어 하나로 때운 정의는 피한다.
    6. 여기까지 같으면 더 짧은 쪽을 고른다. 길이도 같으면 claude를 쓴다.

두 문자열이 앞뒤 공백을 제거한 뒤 완전히 같으면 selectedFrom은 both로 하고 선택 이유를
남길 필요가 없다.

두 모델 모두 규칙을 어겼거나 어느 쪽도 확정 뜻을 제대로 담지 못하면 직접 수정안을 쓴다.
이때 반드시 tmp/defs/RULES.md의 작성 규칙을 그대로 지키고, selectedFrom은 manual로 하며,
검토 보고서에 반드시 넣는다.

어느 한쪽 파일에 해당 wordId가 없거나 JSON이 깨져 있으면 다른 쪽을 쓰고, 양쪽 다 문제면
manual로 처리한 뒤 보고서에 적어라.

**1,200개를 모두 처리하라. 표본만 보고 나머지를 추정하지 마라.**

## 7. 3단계 — sentenceFit 교차 확인

한쪽만 unclear나 mismatch로 본 항목이 특히 중요하다. 한 모델이 잡아낸 문제를 다른 모델이
놓쳤을 수 있기 때문이다. 다음 세 묶음을 직접 확인하라.

    - 두 모델이 모두 mismatch로 본 단어
    - 한쪽만 mismatch로 본 단어
    - 두 모델이 모두 unclear로 본 단어

각각에 대해 final_sentences.jsonl의 sentence를 읽고 실제로 뜻이 어긋나는지 판정한다.
다의어를 특히 주의하라. press, scale, credit, content, charge, beat, state, order, term,
object, board, race, treat, domestic, minute, fine, plant, branch 같은 항목이다.

예문은 확정값이므로 예문을 고쳐 해결하지 마라. 새 정의로 해결하고, 정의만으로 해결되지
않으면 reviewRequired를 true로 두고 사용자에게 보고하라.

최종 sentenceFit 값은 두 모델의 판정을 그대로 옮기지 말고 **직접 판정한 결과**를 적는다.

## 8. 출력 형식

mid1st/final/definitions_v2.jsonl에 final_sentences.jsonl과 같은 순서로 정확히 1,200줄을 쓴다.
빈 줄, 주석, 코드 펜스를 넣지 않는다. 각 줄은 아래 아홉 키만 갖는다.

{"wordId":"DAY01-01","word":"chore","partOfSpeech":"n.","meaningKo":"집안일","definitionOld":"a small job you must do at home","definitionNew":"a small job you do at home","selectedFrom":"claude","sentenceFit":"ok","reviewRequired":false}

    - wordId, word, partOfSpeech, meaningKo : final_sentences.jsonl 값 그대로
    - definitionOld : final_sentences.jsonl의 definition 그대로
    - definitionNew : 2단계에서 고른 정의
    - selectedFrom  : claude | codex | both | manual
    - sentenceFit   : 3단계에서 직접 판정한 ok | unclear | mismatch
    - reviewRequired: boolean

기존 definitions_v2.jsonl이 있으면 덮어쓰지 마라. 유효한 1,200줄이면 검증 결과만 보고하고,
불완전하면 내용을 보존한 채 중단하고 재작업 범위를 보고하라.

작성 후 검증기를 최종본에도 실행해 통과시켜라.

    node mid1st/scripts/validate-definitions.mjs mid1st/final/definitions_v2.jsonl --report mid1st/reports/definition-validation.md

FAIL이 있으면 이 세션이 방금 만든 definitions_v2.jsonl만 고쳐 재검증하라.
형식 검증은 뜻의 정확성이나 쉬운 영어인지를 대신하지 않는다. 통과해도 표본을 뽑아
다의어 정의와 품사 일치를 직접 확인하라.

## 9. 검토 보고서

mid1st/reports/definition-review.md 를 만든다. 첫머리에 다음 수치를 적는다.

    - 두 모델의 기계 검증 위반 건수 (항목별로)
    - selectedFrom별 수 (claude / codex / both / manual)
    - 정의를 바꾼 수와 원문 그대로 둔 수
    - 새 정의의 평균 단어 수와 최대 단어 수
    - sentenceFit별 수
    - reviewRequired 수

그다음 아래 항목만 inventory 순서로 모은다.

    - sentenceFit이 unclear이거나 mismatch인 단어
    - reviewRequired가 true인 단어
    - selectedFrom이 manual인 단어

각 항목에 wordId, word, 품사, 한국어 뜻, 예문, 기존 정의, claude 정의, codex 정의,
최종 정의, 판정 이유를 함께 보여라. 차이가 작다는 이유만으로 표를 늘리지 마라.
